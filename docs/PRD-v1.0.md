# 「药药」短效避孕药拍照记录与提醒产品需求文档

**文档版本：** V1.0
**产品阶段：** MVP
**产品形态：** 微信小程序
**项目代号：** yaoyao
**核心功能：** 药品建档、药板拍照、药位变化识别、人工确认、服药记录、日历及提醒。

---

## 一、产品概述

### 1.1 产品定位

「药药」是一款帮助短效口服避孕药使用者记录每日服药情况的辅助工具。

用户每天通过手机拍摄药板照片，系统识别药板上各个药位的变化，并与此前照片进行比较，提示哪些药位可能发生了变化。

用户核对识别结果后，手动确认当天的实际服药情况，最终形成连续的个人记录。

产品希望解决的核心问题：

- 忘记当天是否已经服药；
- 无法准确回忆某一天是否漏服；
- 仅依靠闹钟提醒，缺少实际记录；
- 药板本身的变化没有被有效利用；
- 无法方便地查看历史服药记录。

### 1.2 核心产品逻辑

产品不是简单的闹钟，而是一个基于药板图像变化的记录系统。

完整流程：

1. 用户建立药品档案。
2. 用户第一次拍摄完整药板，建立药板基准图。
3. 每天拍摄当前药板。
4. 系统识别药板各个位置的变化。
5. 系统将本次照片与历史基准进行对比。
6. 系统展示识别结果。
7. 用户人工确认实际服药情况。
8. 系统保存当天记录。
9. 用户通过首页和日历查看历史记录。

**核心原则：照片识别负责判断药板外观变化，用户负责确认实际服药情况。**

药片从药板中取出，不代表已经吞服。系统不得将两者直接等同。

### 1.3 产品目标

第一阶段目标：

- 建立完整的微信小程序 MVP；
- 跑通拍照、识别、确认、保存的核心流程；
- 验证用户是否愿意每天拍照记录；
- 验证药板识别的可行性；
- 验证用户对提醒和日历功能的实际需求。

暂时不追求复杂的 AI 模型，也不在第一阶段开发复杂的社交功能。

## 二、用户与使用场景

### 2.1 目标用户

使用短效口服避孕药、希望更准确地记录服药情况的女性用户。

### 2.2 典型场景

**场景一：首次使用**

用户打开小程序，建立个人药品档案，选择药品包装和服药安排，拍摄一张完整药板照片。

**场景二：每日记录**

用户打开小程序，点击拍照打卡，对准药板拍照。系统识别药位变化，用户确认当天的实际服药情况。

**场景三：忘记是否服药**

用户查看当天记录。如果药板发生变化但本人无法确认是否实际服药，可以选择「我不确定」，而不是被系统强行判定为已服药。

**场景四：查看历史**

用户打开日历，查看过去某一天的记录、照片和确认状态。

**场景五：提醒**

用户设置每日提醒时间，在平台支持的前提下接收服药记录提醒。

## 三、产品功能需求

### 3.1 用户登录与个人信息

#### 功能目标

为用户建立独立的数据空间。

#### 功能要求

- 支持微信授权登录；
- 每位用户拥有独立用户 ID；
- 用户可以管理个人药品档案；
- 用户可以查看自己的历史记录；
- 用户可以删除自己的照片和记录；
- 用户可以注销或删除账户相关数据。

MVP 可以先使用微信小程序本地开发环境进行功能验证，正式上线再接入完整的用户身份体系。

---

### 3.2 药品档案

#### 功能目标

记录用户当前使用的药品及其药板结构，为后续识别提供基础信息。

#### 需要录入的信息

| 字段 | 说明 |
|---|---|
| 药品名称 | 用户自行填写或选择 |
| 药品品牌 | 可选 |
| 药板数量 | 每板药位数量 |
| 包装类型 | 用户选择或填写 |
| 每日提醒时间 | 用户自行设置 |
| 服药方案 | 根据具体药品说明书填写 |
| 开始日期 | 用户确认 |
| 当前使用状态 | 使用中 / 已停用 |

#### 药板结构

需要支持不同药板规格。例如：21 个药位；28 个药位；其他数量和排列方式。

不能将所有药品硬编码成同一种排列方式。

#### 建档要求

用户完成档案后，进入首次拍照流程。

首次拍摄的完整药板照片作为该药板的初始基准图。后续识别需要基于该基准图和历史照片进行比较。

---

### 3.3 初始药板拍摄

#### 功能目标

建立药板图像基准。

#### 操作流程

1. 用户进入首次拍照页面。
2. 页面显示拍照说明。
3. 用户拍摄完整药板。
4. 系统检查照片质量。
5. 系统提示是否存在模糊、反光、遮挡或药板不完整。
6. 用户确认照片。
7. 系统保存基准图。
8. 进入首页。

#### 照片质量要求

至少需要检查：是否能够识别药板主体；是否存在严重模糊；是否存在明显反光；是否有药位被遮挡；是否存在明显倾斜或透视变形；药板是否完整进入画面。

照片不符合要求时，应提示重新拍摄。

---

### 3.4 每日拍照打卡

#### 功能目标

通过每日拍照形成药板变化记录。

#### 操作流程

1. 用户进入首页。2. 点击「拍照打卡」。3. 调用手机摄像头。4. 拍摄当前药板。5. 显示照片预览。6. 用户确认照片。7. 上传或提交识别任务。8. 等待识别结果。

#### 交互要求

- 支持调用手机后置摄像头；
- 支持重新拍摄；
- 支持从相册选择照片；
- 显示识别加载状态；
- 识别失败时允许重试；
- 照片提交后不能直接认定为服药完成。

#### 拍照说明

建议在页面显示：「尽量保持药板完整入镜，拍摄角度与上次接近，避免反光和遮挡。」

---

### 3.5 药板图像识别

#### 功能目标

识别当前药板与历史药板之间的外观变化。这是产品最重要的技术功能。

#### 识别逻辑

不能只通过简单的图片像素差异判断药位状态。建议采用以下技术流程：

**第一步：图像质量检测** 判断照片是否适合识别。

**第二步：药板定位** 识别药板在照片中的位置，排除背景干扰。

**第三步：图像校正** 通过特征点、轮廓或透视变换，使本次照片与基准图尽可能对齐。

**第四步：药位区域识别** 按照药板结构，将整张药板划分为多个独立药位区域。

**第五步：药位状态识别** 对每个药位判断：

- FILLED：外观显示药位仍完整；
- EMPTY：外观显示药位已经发生取出变化；
- UNKNOWN：无法可靠判断。

注意：这里的 EMPTY 仅代表药位外观变化，不代表药片已被吞服。

**第六步：前后照片对比** 将当前药位状态与上一张有效照片或基准照片进行比较。

**第七步：生成识别结果** 向前端返回每个药位的状态、置信度和变化情况。

#### 识别结果示例

| 药位 | 上次状态 | 当前状态 | 变化 |
|---|---|---|---|
| 1 | FILLED | FILLED | 无变化 |
| 2 | FILLED | EMPTY | 疑似取出 |
| 3 | FILLED | UNKNOWN | 无法判断 |
| 4 | EMPTY | EMPTY | 无变化 |

#### 识别结果页面

需要展示：当前药板照片；药位编号；药位状态；发生变化的药位；识别置信度；识别异常提示。

建议用不同颜色区分：已识别完整；疑似取出；无法判断。

用户点击某个药位时，可以查看对应区域的局部图片。

#### 识别规则

- 低置信度不得直接作为确定结果；
- 药板定位失败时提示重新拍照；
- 新增药板或更换药板时重新建立基准；
- 不允许自动将 UNKNOWN 转换为 EMPTY；
- 不允许将 EMPTY 自动转换为已服药；
- 识别结果必须经过用户确认才能形成最终记录。

#### 技术实现

建议独立开发 Python 图像识别服务：Python；OpenCV；图像透视校正；特征匹配；药位区域裁剪；图像差异检测；识别置信度评估。

第一阶段可以先实现 OpenCV 识别原型，不要求立即训练深度学习模型。识别服务应预留后续接入 YOLO、分类模型或其他视觉模型的接口。

### 3.6 人工确认

#### 功能目标

确保系统记录的是用户确认的实际情况，而不是仅仅根据图片推断。

#### 识别完成后的操作

页面提供三个选项：

**选项一：已按方案服用** 用户确认当天已经实际服药。

**选项二：尚未服用** 用户确认当天尚未服药。

**选项三：我不确定** 用户无法确认实际服药情况。

#### 状态规则

用户确认后，形成以下业务状态：

| 状态 | 含义 |
|---|---|
| PHOTO_PENDING | 照片已提交，等待处理 |
| REVIEW_PENDING | 识别完成，等待用户确认 |
| CONFIRMED_TAKEN | 用户确认已服用 |
| REPORTED_NOT_TAKEN | 用户确认尚未服用 |
| UNCERTAIN | 用户表示不确定 |

识别任务还需要独立记录药位状态：

| 状态 | 含义 |
|---|---|
| FILLED | 药位外观完整 |
| EMPTY | 药位外观显示已发生变化 |
| UNKNOWN | 药位无法识别 |

两套状态不能混为一谈。

#### 特别规则

- 没有拍照不能自动判定漏服；
- 没有确认不能自动判定已服药；
- 用户选择不确定时，保留不确定状态；
- 用户可以修改历史确认结果；
- 修改历史记录需要保留修改时间；
- 用户确认已服用时，应保存确认时间；
- 药板变化和用户服药确认必须分别保存。

### 3.7 首页仪表盘

#### 功能目标

让用户打开产品后快速了解当天记录状态。

#### 首页内容

1. 产品名称与日期；
2. 当天记录状态；
3. 今日拍照打卡入口；
4. 当前药品信息；
5. 本周期记录统计；
6. 连续记录天数；
7. 药板变化概览；
8. 每日提醒时间；
9. 最近几天的记录摘要；
10. 日历入口。

#### 状态展示

首页根据当天状态显示：今日尚未记录；已拍照，等待识别；已识别，等待确认；已确认服用；已确认尚未服用；用户表示不确定。

#### 统计要求

连续记录天数只代表连续存在有效记录，不代表连续服药。

页面应明确区分：记录天数；已确认服药天数；尚未确认天数。

避免将统计数据误解为避孕效果或服药安全评价。

---

### 3.8 日历与历史记录

#### 功能目标

让用户查看过去的记录。

#### 日历功能

- 月历展示；
- 每天显示记录状态；
- 支持月份切换；
- 点击日期进入详情；
- 支持查看照片；
- 支持查看药板识别结果；
- 支持查看用户确认结果。

#### 日历状态颜色

建议：绿色：已确认服用；橙色：已确认尚未服用；灰色：没有记录；黄色：不确定；蓝色：等待确认。

没有记录与确认未服用是两个不同状态，不能混淆。

#### 历史详情

点击某一天后展示：日期；拍摄时间；原始照片；药位识别结果；用户确认状态；确认时间；修改记录。

---

### 3.9 提醒功能

#### 功能目标

提醒用户按自己设置的时间完成记录或确认。

#### 功能要求

- 用户可以设置每日提醒时间；
- 可以开启或关闭提醒；
- 可以修改提醒时间；
- 提醒内容可配置；
- 可以设置是否提醒未完成记录；
- 可以设置是否提醒待确认记录。

#### 提醒文案示例

「今天的药板还没有记录，记得打开药药完成拍照。」
「今天的记录还没有确认，请核对实际情况。」

#### 技术限制

微信小程序不能依赖普通前端定时器实现可靠的后台定时通知。正式版本需要研究并接入微信订阅消息等平台支持的通知能力。用户需要主动授权相应消息。

在订阅消息尚未接通前，提醒功能只能作为前端设置和演示功能，不得宣称后台提醒已经可靠实现。

---

### 3.10 设置页面

功能包括：修改每日提醒时间；开启或关闭提醒；修改药品档案；重新拍摄药板基准图；查看隐私政策；导出个人记录；删除照片；清除本地数据；退出登录；删除账户及相关数据。

数据删除应有明确的二次确认。

## 六、技术架构

### 6.1 总体架构

推荐采用：**微信原生小程序 + CloudBase 云开发 + Python/OpenCV 独立识别服务。**

- 微信小程序负责：页面展示；摄像头调用；用户交互；图片上传；记录确认；日历和历史展示。
- CloudBase 负责：用户数据；药品档案；图片存储；每日记录；数据查询；用户权限。
- Python 识别服务负责：图像质量检测；药板定位；透视校正；药位区域识别；药位变化分析；识别结果返回。

### 6.2 前端技术

微信原生小程序；WXML；WXSS；JavaScript；微信小程序 API。不建议在 MVP 阶段引入过多前端框架和复杂依赖。

### 6.3 后端技术

建议：微信 CloudBase；云数据库；云存储；云函数；Python 独立 API 服务。前后端通过 API 通信。

### 6.4 图像识别 API

**创建识别任务** `POST /api/v1/recognition`
请求：photo_id；medicine_id；image_url；template_id；previous_photo_id。
返回：task_id；status。

**查询识别结果** `GET /api/v1/recognition/{task_id}`
返回：task_id；status；quality_status；positions；changes；error_message。

识别结果示例：

```json
{
  "task_id": "task_001",
  "status": "completed",
  "quality_status": "good",
  "positions": [
    { "index": 1, "visual_status": "FILLED", "confidence": 0.98, "changed": false },
    { "index": 2, "visual_status": "EMPTY",  "confidence": 0.93, "changed": true  },
    { "index": 3, "visual_status": "UNKNOWN","confidence": 0.42, "changed": false }
  ]
}
```

注意：上述 JSON 仅为接口示例。识别服务不返回「已服药」结论。

## 七、核心业务规则

1. 每位用户可以拥有一个或多个药品档案。
2. 每个药品档案可以关联一个或多个药板基准图。
3. 每张每日照片必须关联一个药品档案。
4. 每次照片识别必须生成独立识别任务。
5. 识别任务失败不能生成确定的服药结论。
6. 用户必须人工确认实际服药情况。
7. 每日记录与药位识别结果分开存储。
8. 没有记录不等于漏服。
9. 药位发生变化不等于实际服药。
10. 用户可以修改历史确认结果。
11. 历史修改需要保留修改日志。
12. 用户更换药板后，需要重新建立对应基准。
13. 不同药品的服药方案不得使用统一硬编码规则。
14. 不得根据记录情况自动计算或保证避孕效果。
15. 用户不确定时，必须允许保留 UNCERTAIN 状态。

## 八、隐私与安全要求

照片和服药记录涉及个人敏感信息，正式版本必须考虑：用户授权；隐私政策；数据最小化；图片访问权限；传输加密；存储权限控制；用户数据删除；账户注销；防止不同用户访问彼此的数据。

MVP 开发阶段应优先验证本地数据流程。正式上线前，需要完成微信平台规范及个人信息保护相关合规评估。

---

## 九、产品边界与风险控制

「药药」定位为个人服药记录和提醒工具。

产品不提供：避孕效果判断；怀孕风险评估；漏服后的补服方案；药物剂量调整建议；药品替代建议；医疗诊断；药物治疗建议。

不同短效避孕药的成分、包装和服药方案可能存在差异。涉及漏服后的处理，应以具体药品说明书和专业医疗建议为准。

页面需要明确提示：「药板图像识别仅用于记录药位外观变化，不能证明药片已经吞服。请以个人实际服药情况为准。本产品不能替代药品说明书或专业医疗建议。」

## 十一、开发阶段规划

### 第一阶段：工程梳理

整理现有微信小程序代码；统一目录结构；检查页面跳转；检查数据模型；统一状态定义；完善基础 UI；确保项目可以正常编译运行。

### 第二阶段：核心业务闭环

药品建档；初始药板拍照；每日拍照；照片保存；模拟识别结果；人工确认；保存每日记录；日历展示；历史详情。

这一阶段可以先使用模拟识别结果，不必等待真实算法。

### 第三阶段：真实图像识别

建立 Python API；完成药板定位；完成图像校正；完成药位区域划分；完成药位状态判断；完成前后图片对比；完成置信度计算；完成识别异常处理。

### 第四阶段：云端与提醒

接入 CloudBase；完成用户身份体系；完成云端数据存储；完成图片存储；完成用户数据隔离；接入微信订阅消息；完成数据删除机制。

### 第五阶段：用户测试

重点观察：用户是否愿意每天拍照；完成一次记录需要多久；用户是否能理解识别结果；用户是否愿意人工确认；图片识别失败率；用户连续记录情况；提醒功能是否有帮助。
